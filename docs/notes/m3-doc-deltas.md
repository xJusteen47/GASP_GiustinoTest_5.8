## C3a wire format and C3b rules and hooks (GSTNCombatCore `Sync/`, `Rules/`, `Hits/`; GSTNCombatNP `Simulation/`)

- combat.md (sync state, section on `FGSTN_CombatSyncState`) and combat-m3 7.1: the combat sync state is now `Core` (`FGSTN_CombatSyncCore`: `Input` +
  hitstop window, identical bytes as before) followed by `Fragments` (`TArray<TInstancedStruct<FGSTN_SyncFragment>>`). Field access becomes
  `Sync->Core.Input`, `Sync->Core.HitstopStartFrame` (harness JSON keys unchanged). The M3 fields of 7.1 (`ActionState`, timeline fields...) go into
  `Core`, not into fragments; fragments are for optional features only.
- Wire: `Core`, then 1 flag bit (any fragments); if set, packed count (1..16), then per fragment in ascending type id: 8-bit id, packed byte length
  (max 512), payload. Zero fragments = 1 bit. Length-prefixed (not registry-sized) so an id unknown on a machine is skipped safely, a payload that
  fails to read is dropped without desynchronising the stream, and two builds that disagree on a fragment's size do not corrupt the rest. Cost: one byte per
  present fragment. Bytes do not depend on array order. Measured in the test log: core only 288 bits + 1; one 5-byte fragment +65 bits (353 total);
  a 5-byte and a 4-byte fragment +113 bits (401 total).
- modularity-and-tags 5b table, "Sync-state fragments" row: add "payload is length-prefixed; duplicate ids written once; max 16 fragments of 512 bytes".
  `ShouldReconcile` of the state returns true on a fragment mismatch (a set difference or any fragment's `ShouldReconcile`, default = serialized bytes
  differ); the input state's mismatches are still trace-only, as in M2.
- 5b "Tick extensions" row: type ids come from the same `GSTNFeatureIds` file as fragments (a feature's fragment and extension share the id); order is
  `(Priority ascending, TypeId ascending)`, computed at registration so it cannot change under a simulation; a second extension with a registered type id is
  refused. Four fixed hook points (`EGSTN_CombatHookPoint`): `AfterClocks`, `BeforeCandidates`, `AfterExecute`, `BeforeTagProjection`. Today they surround the
  `FGSTN_InputSimulator::Tick` call (it does candidates, resolution and request in one function, in another plugin), so `AfterClocks` and `BeforeCandidates` are
  consecutive calls before it; the call sites move to their combat-m3 7.2 steps when the model gains the timeline clock (C8/C9) and tag projection (C10).
- combat-m3 7.2: the pipeline of steps 5-7 is `UGSTN_CombatRules::Pipeline`, a list of `TSoftClassPtr<UGSTN_CombatStep>`; per m3-plan Q3 the only step is the
  built-in pass-through `UGSTN_CombatStep_Activation` (the resolver's checks stay in code). `UGSTN_CombatStep` has one `BlueprintNativeEvent`
  `Evaluate(const FGSTN_CombatStepView&) const -> FGSTN_CombatStepResult` (Verdict Continue/Reject, Reason tag); steps run as class default objects
  (stateless). The view is a first cut (Frame, Command, BindingIndex, bActionable, bInTimeline); extend by adding fields. `UGSTN_CombatRules` is in
  `GSTNCombatCore` because it uses no GAS type; a GAS-aware step comes from a GAS-aware plugin's own rules content. The rules asset is not yet read by the
  model (nothing runs `RunPipeline` in the simulation until the model has candidates to filter, C8/C9): `ResolvePipeline()` must be called at BeginPlay, never in a tick.
- combat-m4 3 (`UGSTN_CombatRules`): m4 describes `Pipeline` as `TArray<UGSTN_HitResolutionStep*> Instanced`; C3b creates the asset with the activation pipeline of
  classes. M4 adds its hit-resolution pipeline next to it; align the m4 text with "classes, not instances" and the same step-base conventions.
- combat-m4 5 / modularity 5b "Victim read-model": `FGSTN_HitVictimView` fields: `EntityId`, `TeamId` (byte, 255 none), `Location`, `Velocity`, `FacingYaw`,
  `bInHitstop`, `StateTags`, `Stats` (`FGameplayTag` -> float, entity wide) and `Parts` (`PartName`, `GroupName`, `PartTags`, `State` {Vulnerable, Invincible, Intangible},
  `Stats`). No single health, no single hurtbox.
- `FGSTN_KitExtension` / `FGSTN_KitExtensionList { TArray<FInstancedStruct> ExtensionData }` with `meta=(BaseStruct=...)` exist in Core; the kit and weapon assets of C5
  embed the list.
- testing.md / README: tests `GSTNCombat.Core.Rules.{PipelineOrder,UnknownStepSkipped}`, `GSTNCombat.NP.Fragments.{RoundTrip0,RoundTrip1,RoundTrip2,UnknownTypeId}`,
  `GSTNCombat.NP.TickExtension.{OrderByPriority,EmptyHooksNoEffect}`. The GSTNCombatNP module now has an Automation test directory (`Private/Tests/`); the plugin README
  no longer says it has none. Total 114 headless tests (106 + 8).
- PIE gate (C3a touches the Network Prediction state): `combat_spike` and the M2 scenarios must show identical results to the commit before: no new reconciles
  (the state's `ShouldReconcile` with zero fragments is the old function plus a comparison of two empty lists), the same request/history on server and client, and
  per-pawn sync-state bytes of +1 bit per state compared with the baseline.

Test `GSTNCombat.GAS.Effects.MeterCostCheckApply`; `Attributes.MeterCostSetByCaller` renamed `Attributes.MeterCostData`.

## C6 (compiled binding table, registry, loadout rules)
- combat-m3 9 placement: the compiler is in `GSTNCombatCore` (`Loadout/GSTN_CompiledBindingTable.h`), not `GSTNCombatGAS` as the spec says (modularity 8.1 allows Core where no GAS type appears). Abilities and timeline overrides are opaque `FSoftObjectPath` keys; a thin `FGSTN_LoadoutAssembly` in `GSTNCombatGAS` (`Loadout/GSTN_LoadoutAssembly.h`) turns kit/weapon/super assets into the plain `FGSTN_CompileInput` and `FGSTN_LoadoutRulesView` (parent-chain inheritance, `IsTimelineAbilityClass` = `Combat.Ability.Timeline` asset tag on the class default). The rules live in Core too (`Loadout/GSTN_LoadoutRules.h`).
- combat-m3 9, table shape: `FGSTN_CompiledEntry` carries `SlotIndex` into a table-level `Slots` pool (distinct slots by exported text, first-use order) instead of a copied `Slot`, plus the binding's own `PriorityOffset`/`BufferFramesOverride`; `MakeEffectiveSlot(Entry)` gives the slot with both applied and `Priority` is the rank of that slot. Reason: the validator needs one slot per command, while the rows of a command (grounded/airborne) differ only by binding offsets. `Ability` is an `FSoftObjectPath`, `TimelineIndex` an `int16` (INDEX_NONE for a plain ability). The timeline override is part of the registry pair, not the row. `WeaponCount` is stored for the validator. `WriteBytes` is the deterministic byte form (tags in name order, slots as exported text).
- combat-m3 9, order and registry: rows sorted stably by command tag name inside each source (rows of one command keep their listed order); registry pairs are the timeline rows' `(ability, override)` plus the kit's triggered abilities and passives and the weapons' `PassivesWhileActive` that are timeline abilities (no override), sorted by (ability path, override path, case-sensitive), deduplicated. Timeline = the optional `IsTimelineAbility` predicate, or, when unset, "the row has an override". `GrantedAbilities` = row abilities + kit triggered + kit passives (a weapon's passives are granted when it becomes active), sorted.
- combat-m3 8/9, super code slots: `Command.Super.Slot1..8` are native tags declared in `GSTN_CompiledBindingTable.cpp` (the plan said Core command family; they are declared beside their only user). `FixedSlots`: slot N of the scheme (its command, or `Slot<N+1>` if empty); `PerSuperCode`: `CodeEntry` with command `Slot<N+1>`, pattern steps = `CodeEntry` steps then the super's `InputCode` steps. A super in a slot the scheme cannot serve is an error; one beyond `SuperSlotCount` is a warning.
- combat-m3 8, conflicts: `FindConflicts` runs, per context (kit + weapon W + supers; once if there is no weapon), `UGSTN_InputSlotValidation::FindConflicts` on the effective slots (ambiguous/duplicate/invalid = error, shadowed = warning) and `FindBindingConflicts` + `FindImpossibleBindings` on the rows with `UGSTN_InputSettings::GetAllExclusiveContextGroups()`. The spec's "kit command set + each weapon + supers" is exactly this. Binding conflict messages are prefixed with the context.
- combat-m3 8, rules: `UGSTN_LoadoutRules` is a data asset with an `Instanced` list of `UGSTN_LoadoutRule` objects (Abstract/Blueprintable/EditInlineNew/DefaultToInstanced, one `BlueprintNativeEvent` `Evaluate(const FGSTN_LoadoutRulesView&) -> FGSTN_LoadoutRuleResult{Errors, Warnings}`), not one class with all checks. Built-ins (seven): `KitExists`, `AdditionalWeapons`, `Supers`, `Customisations`, `Skin`, `NoAmbiguousBindings`, `TimelineRegistry`. Returns `FText` errors for the UI as the spec asks. The "replaceable class in project settings" is NOT added yet: the loadout component (C7) points at a rules asset, and the settings key belongs with it. An empty kit tag query (weapons, supers, skins) allows none (the spec says it only for weapons; applied to all three for consistency).
- testing.md / README: tests moved to Core because the code is there: `GSTNCombat.Core.Table.{CompileOrder,CommandSetBaseMinusRemovedPlusAdded,RegistryDedupeAndSort,Customisation,SuperCodeSlots,DeterministicBytes,AmbiguousConflict}` and `GSTNCombat.Core.LoadoutRules.{KitExists,AdditionalWeapons,Supers,Customisations,Skin,NoAmbiguousBindings,TimelineRegistry,DefaultSetAndCustomRule}` (plan names were `GSTNCombat.GAS.Table.*` / `GSTNCombat.GAS.Rules.*`); `GSTNCombat.GAS.Table.AssembleFromDefinitions` stays in GAS. Total 144 headless tests (128 + 16).

## C7 (loadout component, subsystem, save game, skin component; GSTNCombatGAS)
- combat-m3 10 `Revision++` at apply: the revision is bumped when a loadout is ACCEPTED (`AcceptLoadout`), replicated with `Applied`, and the table of every machine is compiled with that value, so server and clients hold the same revision and the same table bytes. A re-apply for a new pawn (respawn, `OnPawnSet`) keeps the revision. The OOB write into the combat sync state stays C8.
- combat-m3 10 flow: the spec's "else on next spawn" is `IsGrantPending()` + `OnPawnSet` (server, applied one tick later so the pawn's ASC has its actor info) + a public `ApplyAppliedLoadout()` to retry. An identical request to the applied loadout is accepted as a no-op (no revision, no broadcast). A refused request is reported to the requesting client by a Client RPC raising `OnLoadoutRejected` (rule findings as `TArray<FString>`; the rules' `FText` errors converted), not by a return value of the RPC.
- Component hooks for tests and games: `ResolveAsset(FPrimaryAssetId)` (default: Asset Manager path, synchronous load, once per id per apply) and `GetTargetAbilitySystem()` (default: the PlayerState's pawn, else the owner's own ASC) are `protected virtual`. `AcceptLoadout` is public (`BlueprintAuthorityOnly`) so a server flow can set a loadout without the RPC. The rules are `Rules` (soft pointer to a `UGSTN_LoadoutRules`; empty = the class default object, the built-in rules); the "replaceable class in project settings" of C6 is therefore a per-component property, not a setting.
- Grant details: the ASC's owner must have authority (`HasAuthority`), a class the ASC already has (a default ability) is skipped and never removed with the loadout, specs have no source object (spike 1: a transient one would keep the fork reconciling), the primary weapon's `PassivesWhileActive` are granted at apply (other weapons' on becoming active: C12), the kit meters (`FGSTN_MeterSetup`) are not applied (their maxima arrive through the stats), `Kit->Stats` init effect before the weapon effect. Resolved assets are kept in a UPROPERTY array; `GetResolvedLoadout()`/`GetCompiledTable()` expose the results to the NP adapter.
- Save game: `UGSTN_LoadoutSaveGame` has its own `SaveVersion` (named so, not `Version`) and relies on `FGSTN_LoadoutData::Serialize` for the loadout; unknown ids are dropped at `LoadLoadout` time on a copy (not when the file is read), because the Asset Manager may not know the ids yet when the subsystem initialises, and so that content that returns restores the preset. A dropped additional weapon re-indexes the customisations of later weapons and removes those of the dropped one; a dropped super leaves its slot empty. Storage and the existence check are virtual on the subsystem (`ReadStorage`, `WriteStorage`, `IsAssetIdKnown`). Save slot name `GSTNCombatLoadouts`, user index from the local player.
- Skins: `UGSTN_SkinComponent` is on the pawn and follows the PlayerState's loadout component (auto-bind with retry, or `BindToLoadout`); it does not hook the pawn's PlayerState replication, hence the retry timer (`MaxBindAttempts`, `BindRetryInterval`). It uses `UGSTN_SkinDefinition` as in C5 and applies mesh, then anim class, then materials per slot; the original look is remembered on the first apply.
- Module: `GSTNCombatGAS.Build.cs` gains `NetCore` (listed explicitly for `DOREPLIFETIME`; Engine already depends on it). No new native tags, no change to GSTNCombatCore or the NP modules.
- testing.md / README: tests `GSTNCombat.GAS.Loadout.{SaveRoundTrip,UnknownIdDropped,RulesRejectInvalid,ApplyOnHostWithoutOnRep}` (4 new; headless total 148 = 144 + 4). Test doubles in `Private/Tests/GSTN_LoadoutTestTypes.{h,cpp}` (component with an id table and a chosen ASC, subsystem with in-memory storage, ability classes A/B/C). The subsystem tests create a `ULocalPlayer` object as the subsystem's outer (`Within = LocalPlayer`) without initialising it. The Server and Client RPC wrappers (`ServerRequestLoadout`, `ClientLoadoutRejected`), `OnRep_Applied`, `OnPawnSet` and the skin component are NOT covered by a headless test (they need PIE with a server and a client).
- PIE gate for C8 (not C7): the first live use of the grants is the spike-1 live tests (L1-L3): one reconcile per accepted loadout, no storm with about 40 specs, client lookup latency.


## C9 (UGSTN_GA_Base, activation context, camera aim; GSTNCombatNP + GSTNInputNP)
- combat-m3 7.10 camera aim: `FGSTN_InputCmd` gains `bHasAim`, `AimYaw`, `AimPitch` (uint16, 65536 steps per turn, `FGSTN_DirectionClassifier::QuantizeAim`).
