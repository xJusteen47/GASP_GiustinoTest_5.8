# M4 doc deltas (for the final docs commit)

Same use as `m3-doc-deltas.md`: what the code did differently from the M4 plan (`m4-hits-plan.md`) and the spec
(`combat-m4-hits.md`, both on the docs branch), to be folded into the docs in the closing commit (H13). The plan says
`Saved/Notes/`; `docs/notes/` is the current rule.

## H1 hit geometry and data (GSTNCombatCore, `Hits/`)

- Plan H1 `FGSTN_HitboxTrack` / `FGSTN_HurtboxModifierTrack`: the C2 tracks are called `FGSTN_TimelineTrack_Hitbox` and
  `FGSTN_TimelineTrack_HurtboxModifier` and already carry `FGSTN_PartSelector`; they stay (names, the M3 validation, the default
  dodge timelines and tests use them) and are completed in `Timeline/GSTN_TimelineTypes.h`, not in `GSTN_HitboxTypes.h`
  (a track derives from the timeline base, which `GSTN_HitboxTypes.h` is included by). Hitbox track: `Hitboxes`
  (`TArray<FGSTN_HitboxSpec>`) beside `Part`. Modifier track: `Part` + `Kind` kept; `State` of the spec is `Kind`, now
  `Invincible / Intangible / Armor` (the resolved per-hurtbox state is the new `EGSTN_HurtState`, with `Normal`);
  added `ArmorThreshold`, `AffectedHurtboxes`, `AffectedTags`, `ShapeOverrides`.
- Spec 3 "`AffectedHurtboxes` (empty = all)": not followed. M3's owner rule stays (a selector with nothing set addresses
  nothing, and the validator reports an error): `Addresses()` is the union of `Part.PartName` / `AffectedHurtboxes` by name and
  `Part.PartTag` / `AffectedTags` by tag (hierarchical); `Part.GroupName` addresses no M4 hurtbox (a hurtbox has no group; the
  parts layer uses it). "All hurtboxes" is spelled by the root tag `Combat.Hurtbox` if every hurtbox carries a leaf, or by
  listing the names. Fail-safe: an empty modifier never makes the whole body intangible.
- `ShapeOverrides` read as "the portion of the addressed hurtboxes the state covers" (spec 1b: "which portion of them"), not as a
  replacement shape. `FGSTN_TimelinePlayer::ResolveHurtState` leaves a modifier that has portions out; the H4 `HurtState` step
  decides with the contact point.
- Plan "`FGSTN_TimelineFrameResult`, M8 §3 shape": delivered as a separate `FGSTN_TimelinePlayer::EvaluateHits(Data, Frame,
  Result)` (Frame = timeline frame minus paused frames, as `FGSTN_TimelineOutput::Frame`) with `FGSTN_ActiveHitbox { Spec, Track,
  TrackFrame }` and the open modifier tracks; `Evaluate` and `FGSTN_TimelineOutput` are unchanged. The per-hurtbox state is
  `ResolveHurtState(Result, Hurtbox)` returning `FGSTN_HurtboxFrameState { State, ArmorThreshold }` (Intangible > Invincible >
  Armor, armor keeps the larger threshold, infinite beats a number).
- Key frames of a hitbox (`FGSTN_HitboxKey::Frame`) count from the start of the track; `BakedSockets` are indexed by timeline
  frame. Keys must be sorted (validator error otherwise). Rotation interpolates by slerp, offset and scale linearly; outside the
  keyed range the nearest key holds.
- `FGSTN_CombatTimelineData::BakedSockets` is `TMap<FName, FGSTN_BakedSocketFrames>` (a struct with `TArray<FTransform> Frames`),
  not `TMap<FName, TArray<FTransform>>`: a nested container is not reflectable. `FindBakedSocket(Socket, Frame, Out)` clamps the
  frame (past the end the last transform holds).
- Capsule extent convention: `Extent.X` = radius, `Extent.Z` = half height including the hemispheres (Unreal's), axis = local Z,
  `Extent.Y` ignored. Sphere uses `X`. Scale: sphere by the largest component, capsule radius by the larger of X and Y, half
  height by Z, box per axis.
- Sweep: N = ceil(travel of the shape's centre / smallest world extent), clamped to [1, 4], samples at i / N for i = 0..N
  (so up to five tests, the endpoints included). Only the centre's translation sets N: a hitbox that only rotates in place takes
  one step (its rotation is still interpolated when it also translates). Documented in the header; revisit with the M5 baked
  swings if tunnelling shows up.
- Capsule vs box is exact (no sampling): the squared distance from the segment to the box is convex and piecewise quadratic,
  split at the face-plane crossings, and minimised in closed form per piece.
- `FGSTN_HitData::ExtraEffects` is `TArray<TSoftClassPtr<UObject>>`, not `TSubclassOf<UGameplayEffect>`: Core has no
  GameplayAbilities dependency. H5 resolves and validates them in `GSTNCombatGAS`.
- `FGSTN_HitDataOverride` is "which fields (bit mask `EGSTN_HitDataField`) take the value from `Values`" + multipliers +
  `ExtensionOverrides`, not a struct of optionals. Order in `ApplyVariant`: replace, then multiply (a negative
  `FixedKnockback` stays unused), then extensions replaced by struct type (appended when the hit has none).
  `FGSTN_HitExtensionOverride` of plan H4 is not needed: the override list holds `FInstancedStruct`s of `FGSTN_HitExtension`
  (`GSTN_HitExtensions.h` carries only the base struct in H1; H4 adds appliers there).
- Types the plan puts in H2/H3 but that H1's structs need are declared early in their final files, minimal: `GSTN_ReactionTypes.h`
  (`EGSTN_HitReaction`, `FGSTN_StaggerThreshold`, `FGSTN_HitReactionModifiers`, `FGSTN_BakedCurve`) and `GSTN_ImpactTypes.h`
  (`EGSTN_ImpactOutcome`, `FGSTN_ImpactProfile`). Differences H2/H3 must keep or change on purpose:
  `FGSTN_HitReactionModifiers::StaggerThreshold` is an `FGSTN_StaggerThreshold` (`Value` = -1 unset, `bInfinite`) instead of a
  float, so super armor works on a hurtbox; `FGSTN_BakedCurve` is `USTRUCT()` with `TArray<uint16> Samples` (Blueprint has no
  16 bit integer, so the property is not exposed; 64 samples = authored, empty = unset) and has no evaluation yet;
  `FGSTN_ImpactProfile::Forbid` is `TArray<EGSTN_ImpactOutcome>` (outcomes are an enum, not tags).
- `UGSTN_HurtboxSetDefinition` is a plain `UDataAsset` (no primary asset type to register); `Hurtboxes` is the array the
  `HurtboxIndex` points into.
- Tags: `Hits/GSTN_CombatHitTags.h` (not in `GSTN_CombatCoreTags.h`): `Combat.Hurtbox` (root), `Combat.HitType.*`,
  `Combat.Relationship.*`. The hurtbox leaves are in `Plugins/GSTNCombat/Config/Tags/GSTNCombat.ini`. The engine does not scan a
  plugin's `Config/Tags`: `GSTNCombatCore` registers the folder in `StartupModule` (`AddTagIniSearchPath`, new private dependency
  `Projects`). A loose tag ini reads a plain `GameplayTagList=` line per tag; the `+GameplayTagList=` form loads nothing.
- Validator (`FGSTN_TimelineValidation`): hitbox shape without volume (error), a `BakedSocket` hitbox with no socket name (error),
  a socket with no bake or a bake shorter than the timeline (warnings), unsorted keys (error), `HitType` other than Normal on the
  hit or on a variant that overrides it (warning, plan assumption M4.13), an Armor window with no threshold (warning). A
  modifier addressed only through the new lists is a valid selector.
- Not done in H1 (on purpose): the reach logic (`ReachAxis` / `bScaleExtentWithReach` are data, M11), the same-group priority
  rule for sweet/sour spots (H8), the hurt state as a pipeline step (H4), `FGSTN_HitVictimView` completion (H2).

## H2 reaction model (GSTNCombatCore, `Hits/`)

- Files as the plan lists them, plus `GSTN_ReactionValidation.h/.cpp` (`FGSTN_ReactionValidation::ValidateTuning`, `ValidateModelWithCurve`; its own `FGSTN_ReactionMessage`, not the timeline's) and `GSTN_ReactionTypes.cpp`. The pre-declared types were completed, not redefined: `FGSTN_StaggerThreshold` (value + `bInfinite`) is used by `FGSTN_HitReactionModifiers` and by the stagger test; `FGSTN_BakedCurve` kept `TArray<uint16> Samples` and gained the evaluation / baking.
- `FGSTN_BakedCurve` encoding (the plan only said "64 x uint16, integer interpolation"): Q2.14 (16384 = 1.0, so up to about 4), the input is quantised to 1/4096 and the rest is integer arithmetic; NaN reads as 0; an unauthored curve evaluates to 1.0 (`One`) and is not `IsFlat()`.
- `FGSTN_VictimReactionState` is a plain trivially copyable struct (not a USTRUCT: it holds `uint16`, which Blueprint cannot expose) with `Make()` doing the quantising: percent in tenths, weight scale in 1/64, `EffectiveThresholdQ` an `FGSTN_StaggerThreshold` rounded to whole units. Flags are the constants of `GSTNVictimReactionFlags`. `FGSTN_HitVictimView` got `HealthFraction`, `Weight`, `ReactionState` and a non reflected `const void* SnapshotExtension` (the "pointer to the extension POD"); the M8 fields it already had are untouched.
- `FGSTN_KnockbackInput` is the plan's "(hit, input)" folded into one struct: it holds `Hit` itself. Added fields the formulas need and the plan did not name: `LaunchDirection` (unit, H3 builds it), `Up` (victim's local up, for the push back), `Weight`, `DamagePercent`, `HealthFraction`. `FGSTN_KnockbackResult` added `Knockback` (K after `KnockbackScale`).
- Model structure: `UGSTN_KnockbackModel::Compute` (BlueprintNativeEvent) = `ResolveRules(Input, ComputeKnockback(Input))`; subclasses override only the protected pure virtual `ComputeKnockback` (K before `KnockbackScale`). `Tuning` (`FGSTN_ReactionTuning`) is a property of the base. Rules in `ResolveRules` follow the plan's order exactly.
- Hitstop Auto uses the **real K** (after `KnockbackScale`) in `HitstopPerKnockback`, per the plan ("Auto from real K and real damage"), not the `NominalKnockback` of the older spec text. Both sides use the same `Base`.
- Push back: horizontal = launch direction projected on the plane normal to `Input.Up`; when the direction lies along `Up` there is no horizontal part and the velocity is 0. Promotion to `Launch` when airborne or on a wall stays in H9 (needs the movement state).
- Formulas the spec left open (documented in the header, tested with hand values): `PercentScaling` is the platform fighter formula with every constant a property (`P = DamagePercent + Damage`, `K = ((P/10 + P*Damage/20) * 200/(EW+100) * 1.4 + 18) * Growth/100 + Base) * UnitScale`, `UnitScale` 10 cm/s); a `FixedKnockback >= 0` is the whole K there (no percent, no weight), while in `WeightDriven` it replaces only the bracket and the weight still applies; `CappedPercent` is `PercentScaling` with the percent clamped to `PercentCap` (default 100); `Fixed` is `FixedKnockback` else `BaseKnockback` (no growth, percent or weight).
- C++ defaults of `FGSTN_ReactionTuning` are neutral starting points, not the plan's rules asset numbers: `StaggerPerDamage` 1, `StaggerPerKnockback` 0, `HitstopPerDamage` 0.3, `HitstopBase` 3, `MaxHitstop` 20, `TumbleThreshold` 1800, `HitstunFactor` **0.02** frames per cm/s (the plan's "0.4 frames per cm/s" would be 720 frames at the tumble threshold: to settle with the owner when the standard rules asset is written in H4), `MinHitstunFrames` 6, `PushBackSpeedScale` 1, `MaxPushBackSpeed` 600, `WeightReference` 100, `MinWeight` 1. Tier thresholds 0 as specified.
- Validator: `PushBackThreshold <= LaunchThreshold <= TumbleThreshold` (errors), non positive `WeightReference` / `MinWeight` (error), `MaxHitstop == 0` (warning), a curve whose sample count is neither 0 nor 64 (error), a model with `UsesPercentTerm()` next to an authored non flat curve (warning). `UsesPercentTerm()` is a virtual on the model.
- Test additions beyond the plan list: `PushBackOnVictimUp` (tilted up, never world Z), `BitwiseIdentical` (300 LCG inputs through the four models on two runs, compared field by field). Test tunings use binary exact fractions (0.25, 0.0625, 0.0078125) because `0.01f * 500` floors one frame short.
- Not done (on purpose): `KnockbackResistance` (H9, velocity only), the stagger lock floor (H9), `AirborneJuggleScale` (rules, H4), the `HealthWeight` step that writes `WeightScale` (H4).

## H3 DI and impact math (GSTNCombatCore, `Hits/`)

- Files as the plan lists them: `GSTN_HitMathUtils.h/.cpp`, `GSTN_ImpactTypes.h` (completed), `GSTN_ImpactMath.h/.cpp` (also holds `UGSTN_SurfaceImpactTable` and `FGSTN_ImpactResponse::Find`), root tag `Surface.Type` in `GSTN_CombatHitTags` (also in `GetDeclaredHitTags`), leaves `Wall`, `Glass`, `Crate`, `Trampoline` in `Config/Tags/GSTNCombat.ini`.
- `ApplyDI` takes one more input than the plan's signature: `YawSourceDirection`, the horizontal fallback of step 1 for a launch along `Up` (the spec says "the hit's YawSource direction" but a stateless function has to be given it). Stick strength is `min(|Stick|, 1)` (linear, scale 1, as M4 says); the stick is projected onto the plane again inside, so a caller that forgets is safe. Sign convention: the stick along the launch's horizontal part is DI **out** (+1), against it DI **in**; positive lateral (stick along `Up x h`) turns by `+MaxDIYawDegrees` (right handed about `Up`).
- `LaunchDirection` also takes `bVictimGrounded`, `Knockback` and `FGSTN_SakuraiParams` (low angle 0 deg, high 44 deg, threshold 800 cm/s: starting values, the spec only describes the behaviour "low on grounded below a knockback threshold, higher in the air") because `Sakurai3D` needs them. Fallback chain for a yaw source with no horizontal part: attacker facing, direction to the victim, a fixed direction on the plane. `AutoLink` = the hitbox velocity's own 3D direction, the normal yaw source and angle when it has none; a zero `Up` returns the zero vector.
- **H4 note**: `Sakurai3D` needs the knockback `K` before the direction exists, and `FGSTN_KnockbackInput` needs the direction. The model is pure, so the `ComputeKnockback` step calls `Compute` once with a zero direction to read `Knockback`, builds the direction, then calls it again with it (or H4 adds a public `K` accessor to the model).
- Impact types: `FGSTN_ImpactProfile::Forbid` stays `TArray<EGSTN_ImpactOutcome>`; added `bForceIgnoresSurface` to it. The "allowed outcomes" of the surface and of the victim are `FGSTN_ImpactAllowed` (three bools, `None` always allowed). `FGSTN_ImpactInput` is a plain struct (`uint8` row, `uint16` whole cm/s; Blueprint has no 16 bit integer), `FGSTN_ImpactResult` a BlueprintType struct.
- Resolution order, exact (spec 7b is silent where noted): (1) a row with `bForceDefault` (new, for the trampoline: "its row forces Bounce") is the physical truth and beats the attack's Force / Forbid and the victim; (2) else the attack's `Force`, unless it is in `Forbid`, when the surface allows **any** outcome or the profile has `bForceIgnoresSurface` (the forced outcome need not be one the surface lists: glass allows only breaking, a forced splat still splats); (3) else the surface default if the surface, the victim and the profile's `Forbid` all allow it; (4) the speed `ImpactSpeedQ x SpeedScale` must be **greater than** the larger of the surface's and the victim's `MinImpactSpeed` (a victim can raise the threshold, never lower the surface's), else `None`. The victim's restitution / splat frames replace the surface's when >= 0; damage scales multiply.
- `UGSTN_SurfaceImpactTable`: `Compile()` (at `PostLoad`, after an edit, and called by code that fills `Rows`) builds `TMap<FGameplayTag, int32>`; first row of a tag wins; at most 254 rows (255 = no surface type); lookup is exact then nearest parent tag, and `FGSTN_ImpactResponse::Find` matches hierarchically (`MatchesTag`).
- `GoldenMatrix`: the plan says "compared with a golden file"; the golden is an inline string in the test (worked out by hand from the rules, 4 surfaces x 2 victims x 5 profiles), not a file: there is no golden file mechanism in this plugin and a string beside the code cannot go missing. The "printed by the validator" part is not done (no validator for impact tables yet; H13 content validators).
- Test additions beyond the plan list: `Hits.DI.LaunchDirection`. `SpeedUnchanged` also checks bitwise equality over 500 LCG cases on two runs. The DI tests that read an elevation compare to 1e-6 because `FGSTN_DIParams` holds floats (0.2f is not 0.2).
- Not done (on purpose): the contact probe and `SurfaceTypeIndex` in the tumble contact record (H11), `IGSTN_ImpactSurface`, physical material to tag mapping (H11), the DI strength curve / victim tag scales (M6).

## H4 pipeline, rules and generic seams (GSTNCombatCore, `Hits/`, `Rules/`; commits H4a 37d10fd, H4b 67033af)

- Files as the plan lists them, plus `Hits/GSTN_RelationshipResolver.h` (resolver and query; it landed in H4a, not H4b, because the `TeamFilter` step needs it) and `Private/Tests/GSTN_PipelineTestTypes.h`. `FGSTN_HitExtensionOverride` is not a separate struct: relationship variants already replace extensions by struct type through `FGSTN_HitDataOverride::ExtensionOverrides` (H1, test `VariantExtensionOverride`).
- **Hit pipeline is a second list.** The rules keep `Pipeline` (activation, `TSoftClassPtr<UGSTN_CombatStep>`) and gain `HitPipeline` (`TSoftClassPtr<UGSTN_HitResolutionStep>`), instead of one list shared by both: a hit step in the activation list would be a silent pass-through and an activation step in the hit list a skip. Steps are classes (CDO, stateless) as in C3b, not instanced objects, so a step has no tunables of its own; the tuning lives in the rules. `UGSTN_HitResolutionStep` still derives from `UGSTN_CombatStep`.
- `FGSTN_HitResolutionContext` is a plain C++ struct (not reflected); the Blueprint face is `FGSTN_HitContextView` (a copy, plus two non-reflected pointers: the rules and the hurtbox set). `FGSTN_StepResult` is the delta (scales multiply, a set threshold replaces, `MaxReaction` takes the lower, flags OR, lists append). The context also carries `HurtState`, `ArmorThreshold`, `bNoDamage` and `HurtboxSet`, which the caller fills (the plan said "HurtState records it in the context"; the caller resolves the state with `ResolveHurtState`, the step acts on it). The outcome got `bHasKnockback` (false = no model ran) and requests are typed (`EGSTN_HitRequestKind` Damage / MeterGain / Knockback / Freeze, target Victim / Attacker), not tags.
- **K and the direction (H3 note):** `ComputeKnockback` calls `Compute` twice only for `Sakurai3D` (once with a zero direction to read K, once with the direction); every other special angle calls it once. No K accessor was added to the model. K does not depend on the direction, so the second result is complete.
- Rules additions the plan did not list: `MaxHealth` (the cap of `PercentCapped`, the full health of `Health`, the percent at which the health curve ends in `Percent`), `Sakurai` (`FGSTN_SakuraiParams`), `MeterGainMeter` and `MeterGainPerDamage` (default 0 = the `MeterGain` step writes nothing). `GetDamageProgress`: `Health` = 1 - `HealthFraction`, the percent modes = damage percent / `MaxHealth`, clamped to 0..1. The standard `DamageMode` is `Percent`.
- `HittableRelationships` empty means Enemy and Neutral (the class default is not written because a CDO is built before the native tags exist); `CreateStandard` writes the two tags. `Self` is hittable only when listed, `bFriendlyFire` adds `Ally`.
- `AirborneJuggleScale` is applied in `ComputeKnockback`: a victim whose reaction state carries the Tumble flag has its `KnockbackScale` multiplied by it (default 1). `KnockbackResistance`, the stagger lock floor (`MinStaggerLockFrames` is stored, unread) and the push back promotion stay in H9.
- Numbers (HitstunFactor): kept at 0.02 frames per cm/s. With the standard thresholds a push back at 540 cm/s gives floor(10.8) = 10 frames (`MinHitstunFrames` 6 is the floor), a launch at 1080 gives 21, a tumble at 1800 gives 36. The plan's 0.4 would give 432 frames at 1080, so it stays a unit slip; to settle with the owner when the asset is tuned.
- **Standard rules asset: pending (editor).** `GSTN_CombatRules_Standard` was not created (no editor in this session). `UGSTN_CombatSettings::DefaultRules` null means the built-in standard rules (`UGSTN_CombatRules::CreateStandard`, same values as the plan, covered by `StandardRulesBuiltIn`); `ResolveDefaultRules()` loads the asset when it is set. When the asset is made in the editor, set it as `DefaultRules` in `Config/DefaultGSTNCombat.ini` and keep the two in step.
- Validator (`FGSTN_CombatRulesValidation`): step order (a step that feeds the model after `ComputeKnockback` is an error, `Hitstop` before it a warning), unknown entry (error) vs known placeholder (warning), duplicates, `HealthWeight` with `PartResolve`, tuning and percent-term model next to a non flat curve (the H2 checks), `MaxHealth`, `MaxRewindMs`; `ValidateHitstopOverride` for the hitstop override above `MaxHitstop`. Not done: "hurtbox `ReactionScale` and a part reaction both set" needs the part type of GSTNParts, which does not exist; the hook is the same function when it does. `IsDataValid` of the rules runs `Validate`. Steps are compared by their short name (class name without `GSTN_HitStep_`).
- `PrintReactionMatrix` takes plain victim rows (name, weight, threshold, cap) and hit columns and returns text ("-", "In", "Push", "Launch", suffix "T" for tumble), at full health with the rules' model; the golden is an inline string in the test (as in H3).
- Appliers: `Apply(Extension, View, Context)` with `FGSTN_OutcomeApplyContext { FGSTN_SyncFragmentArray* VictimFragments; FGSTN_OutcomeApplyResult Result }`, so a C++ applier writes its fragment at F+1 and returns events and effects. The Blueprint adapter returns only the result struct. Registry order: CRC32 of the struct path name, ties by the path; native appliers first, then the rules' Blueprint ones in array order. `FGSTN_OutcomeApplierRegistry` and `FGSTN_AttackerOutcomeRegistry` have `Get()` for the shared instance and are plain classes so tests build their own. Nothing in Core or the combat tick calls `ApplyAll` yet: H9 does when it applies an outcome.
- Hit group mask: `FGSTN_HitGroupMask` (256 bits) is an out field of `FGSTN_CombatTickContext` (GSTNCombatNP), fresh every frame, rather than a changed signature of `OnCombatHook`; nothing reads it until H8. A set bit means "this group does not hit".
- Tests beyond the plan list: `StandardRulesBuiltIn`. `BlueprintStepRoundTrip` is pending for H13 (needs a Blueprint step asset, no editor work in this session). `HitGroupMaskDefaultEmpty` covers the Core type only; the NP context default is exercised by the existing tick extension tests.

## H5 GAS: damage, attributes, effects, events (GSTNCombatGAS; commit 25ac7de)

- **Attribute set name:** `UGSTN_HealthAttributeSet` (plan H5 / coordinator "one set per concern"), not the spec section 4 wording that puts the health attributes into `UGSTN_CombatAttributeSet`. Defaults (`MaxHealth` 100, `Health` 100, multipliers 1, the rest 0) are in the plugin's `Config/DefaultGSTNCombatGAS.ini`, MaxHealth before Health. The two stale "no health here" comments of the other sets were updated.
- **PercentCapped cap lives in the execution, not in `PreAttributeChange`:** the set cannot know the damage mode (a clamp at `MaxHealth` would also cap the plain percent mode, where 999% is normal). The execution adds only `clamp(MaxHealth - DamagePercent, 0, damage)`, so the percent stops exactly at the cap. The cap is the target's `MaxHealth` attribute, not `UGSTN_CombatRules::MaxHealth`; the hit applier (H9) must write the rules' value into the attribute when it grants the sets, or a game sets it in its kit init effect. To settle in H9.
- **DamageMode reaches the execution through a local pointer in the context:** `FGSTN_HitEffectContext::Rules` is a weak pointer, not serialized and not in the spec's field list. A context without rules (a plain stock context, or one received over the network) counts as `Percent`. The execution never calls `ResolveDefaultRules` (it could load an asset inside the simulation).
- **Context fields beyond the plan's list:** `HurtboxIndex` and `KOReason` (serialized), so one handle carries the whole `Hit.Received` payload; `FGSTN_HitEventPayload` is a view of the context (`MakeEventData`/`FromEventData`), because a gameplay event can carry structured data only through its context handle. Net format: four packed indices (shifted by one so INDEX_NONE costs one byte), `FVector_NetQuantize10`, two tags, the reaction byte, one bit.
- **No AbilitySystemGlobals subclass:** the project allocates plain contexts today, so there was no registration path to extend, and a custom allocator needs `AbilitySystemGlobalsClassName` in a project ini (untouched). `FGSTN_HitEffectContext::Make` builds the handle for `MakeOutgoingSpec`. If the owner wants ASC-made contexts (`MakeEffectContext`) to be hit contexts, a globals subclass plus one ini line is the follow-up.
- **Tags:** `Combat.State.Hitstun` and `Hitstop` already live in the core, so only `Combat.State.Tumble` was added here. `Combat.SetByCaller.Meter` was not in C4, so it is added. `Input.BufferEvent.HitReceived` is NOT added: **pending owner answer (plan section 6)**; the test list and the tag list do not reference it. `Combat.Event.Impact` is a root only (leaves come with H11); `GameplayCue.Combat.Hit` root only. Everything native, none in ini, all listed in `GetDeclaredTags`.
- **Rules component:** `ApplyRules` loads the asset and runs `ResolveHitPipeline` on it, or takes `UGSTN_CombatSettings::ResolveDefaultRules()` when the reference is empty or does not load (logged). It is called from `BeginPlay`, `OnRep_RulesAsset` and `SetRulesAsset` (authority only). The GameState Blueprint wiring is still the owner's decision (plan section 6); nothing was added to any Blueprint.
- **Not in H5:** the KO condition (H9); the code that builds the context and applies the four effect classes of the rules from a hit outcome (H9, uses `Make` and `UGSTN_GE_Damage`/`UGSTN_GE_MeterGain`); `KnockbackEffect`/`FreezeEffect` classes (H6-H9). `UGSTN_GE_Damage` and `UGSTN_GE_MeterGain` are plain classes; the rules fields stay `TSoftClassPtr<UObject>` and a default of the standard rules naming them is H9/H13 work.
- Tests: the 8 listed, all with a transient stock ASC (`FRig` now adds the health set after the combat and meter sets). `GSTNCombat.GAS.Tags.AllRegisteredAndDocumented` covers the new tags too (they are in `GetDeclaredTags`). 302 GSTN tests, headless, exit 0.

## H6 NP: sync state, world subsystem, snapshot, inbox (GSTNCombatNP; commits e8b1898, dd7212d)

- **Bytes (printed by `GSTNCombat.NP.Hits.State.RoundTrip`, bit archives, whole combat sync state with the input history of one frame):** idle 291 bits (37 bytes, the same as before H6: the hit part sits inside the action part, whose bit an idle combatant already pays); running a move with no hit 372 bits (47 bytes); attacker that has hit one victim (origin, one target, one confirm flag) 513 bits (65 bytes, +141 bits for the hit part: 1 live bit, 7 presence bits, 2 reaction bits, the origin at about 14 bytes, the target 2 bytes, the flags 1 byte); victim in hitstop with a tumbling launch (Tumble, hitstun end, pending launch, three requests) 529 bits (67 bytes). Costs outside the hit part, paid only by a non idle action part: +1 bit for the action state (3 bits), +1 bit per request (type is 4 bits), +1 bit "hit part live". `IdleZeroCost` checks that idle and expired states are bit equal to the baseline measure of `GSTNCombat.NP.State.RoundTrip`.
- **The inbox registry of C3 does not exist in code.** Only the design (modularity-and-tags 5b: `FGSTN_InboxEntry` with an open payload, `PostToInbox`) was written; nothing registers kinds. H6 ships the typed container `FGSTN_HitInbox` (+ `FGSTN_HitInboxEntry`) on the victim component, with the drain order of the spec. The generic registry (open payload, handler per kind) is left for the first second kind of message (M6 links); `FGSTN_HitInbox` is the hit kind of it, so the entry type and the drain keys do not change.
- **Hit part inside the action part, canonical on the wire.** Every field expires by its end frame, and instead of the combat tick clearing a window that ran out, `FGSTN_HitSyncState::Canonical(context)` drops it (context = the state's own latest frame, timeline start, hitstop end). Canonical is what `NetSerialize` writes and `ShouldReconcile` compares, so expired leftovers are neither bytes nor a reconcile. Liveness rules: origin, confirm flags and targets live while `ActionState == InTimeline` (a target also needs `TimelineStartFrame` equal to the core's, which is why it is not on the wire); hitstun and impact end live while the stamp is in the future; pending reaction, pending launch and SDI count live while `HitstopEndFrame` is in the future. The component registers when its NP id is valid (a client's arrives by replication, after BeginPlay: `TickComponent` retries), unregisters in `EndPlay`, and `RestoreFrame` invalidates. The development assert is an `ensureMsgf` in `EnsureSnapshot`: a frame older than the held one with no invalidation in between means a rollback skipped an instance.

## H9 (final: victim side complete, rollback fixed, all scenarios): deltas to the plan and the spec

- **Findings that shaped the scenarios:** (1) the first hit freezes its victim and a frozen move does not advance, so in a flinch trade the second hit comes up to 8 frames after the first; with a staggering trade the first hit cancels the other move one frame later unless the two hits are on the same frame, so `hit_trade` has a flinch round (both land, judged strictly) and a staggering round that accepts either outcome and judges every hit that landed.
