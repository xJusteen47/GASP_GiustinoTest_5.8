# Testing the GAS + NPP + Mover integration

Two layers: Automation tests for the pure input and combat logic (`GSTNInputCore`, `GSTNCombatCore`), and a PIE network harness for everything simulated.

## Automation tests (`GSTNInput.Core.*`, `GSTNCombat.Core.*`)

Pure, deterministic tests. `GSTNInput.Core.*` (input history, classifier, matcher, slots, resolver) live in `Plugins/GSTNInput/Source/GSTNInputCore/Private/Tests/`; `GSTNCombat.Core.*` (the standard command set, the combat tags and the project's combat settings) in `Plugins/GSTNCombat/Source/GSTNCombatCore`. 94 tests today across `GSTNInput.Core`, `GSTNInput.NP` and `GSTNCombat.Core`. Run them in the editor (Session Frontend > Automation, filter `GSTNInput` or `GSTNCombat`) or headless with the editor closed (the command runs both prefixes; a second `RunTests` in the same `-ExecCmds` may be dropped, so use `+`):

```
"C:\Program Files\Epic Games\UE_5.8\Engine\Binaries\Win64\UnrealEditor-Cmd.exe" "<project>\GASP_Giustino2.uproject" -ExecCmds="Automation RunTests GSTNInput+GSTNCombat;Quit" -unattended -nullrhi -nopause -log
```

The result is in `Saved/Logs/GASP_Giustino2.log` (search `Test Completed`). Test names are `GSTNInput.Core.<Area>.<Case>` and `GSTNCombat.Core.<Area>.<Case>`; sources are in `Private/Tests/`. `GSTNCombatNP` (plugin `GSTNCombatNP`) has no Automation tests; the combat model is covered by the PIE harness below.

`GSTNInput.NP.*` (in `Plugins/GSTNInputNP/Source/GSTNInputNP/Private/Tests/`; the module moved from the `GSTNInput` plugin to the new `GSTNInputNP` plugin, test names and the `RunTests GSTNInput+GSTNCombat` filter are unchanged) tests the input simulator against a mock host, without a world: `Simulator.*` (requests, buffer, forced commands, unbound commands, `Locks.Global`, `Locks.Root`, `CommandExecutedEvent`), `Bindings.Table`, `Context.ActivationContext`, `Component.Standalone` (the standalone component's defaults and its sync state round trip). Added in S2c-S2e: `GSTNInput.Core.Input.Locks.*` (lock tag mapping, roots, global lock), `GSTNInput.Core.Input.Events.*` (outbox, query, dispatcher, reentrancy, subsystem) and `GSTNCombat.Core.Locks.NativeRoots`. The `GSTNInput.NP` and `GSTNCombat` prefixes run with the same `RunTests GSTNInput+GSTNCombat` command. Added with the independence work: `GSTNInput.Core.Input.Blueprint.*` (the Blueprint wrappers of conditions, priority criteria and reset rules, against native stand-in classes), `GSTNInput.Core.Input.Settings.Contributions`, `GSTNInput.NP.Context.BlueprintProvider` and `GSTNCombat.Core.OwnSettings` (the combat plugin's own config file and its contribution to the input settings).

## C++ side (`GASNPPTest/`)

- `UGSTN_GASNPPTestComponent` (on `BP_GASNPP_TestCharacter`): registers the test mapping context on the local pawn, counts Mover rollbacks and simulation ticks (and how many were re-simulations), injects input (`StartHoldingInput`, `StopHoldingInput`, single-frame press) and exposes `GetStateSnapshot()`: a JSON of role, counters, transform/velocity/mode, attributes, tags, active effects, cooldowns. Server and client copies of the same pawn are compared through it.
- `GSTN_TestAbilities`, `GSTN_TestAttributeSet`, `GSTN_TestEffects` (Dash, Buff, stamina regen): throwaway content that exercises prediction, cost, cooldown, attribute modification.
- Game mode `GM_GASNPPTest`, input `IMC_GASNPP_Test`, `IA_GASNPP_Dash`, `IA_GASNPP_Buff`.

## Python side (`Tools/GASNPPTest/gasnpp_test.py`, run in the editor Python console)

**Primary configuration: listen server.** One player hosts and plays, the others are clients; "Run Under One Process". World 0 is the host (its pawn is authority **and** locally controlled), worlds 1..N are clients. The dedicated server (world 0 with no local player, clients 1..N) stays as a secondary check.

```python
import sys; sys.path.insert(0, r"<project>/Tools/GASNPPTest"); import gasnpp_test as m
m.setup_editor(True)          # before Play: test GameMode + PIE settings = listen, host + 2 clients (not saved), no CPU throttling
                              # secondary check: m.setup_editor(True, 'dedicated', 2)
m.net(60, 15, 2)              # lag ms, jitter ms, packet loss %
m.check_topology()            # after Play: (mode, problems); [] = roles are what the mode promises
m.reset_all(); m.scenario_abilities()   # every player, the host included; or scenario_forced_rollback / scenario_server_correction / scenario_accounting
print(m.report())             # counters + authoritative copy vs every other world's copy of each pawn
m.setup_editor(False)         # after Stop: restore GM_Sandbox, throttling and the PIE settings
```

- `LevelEditorPlaySettings` is **not exposed to Python** in 5.8 (checked live), so `setup_editor` only does the GameMode and throttling part and returns what to start PIE with. Start PIE with the play tool (Rider MCP `ue_play`: `netMode=listen, players=3, runUnderOneProcess=true`; dedicated: `netMode=client, dedicatedServer=true, players=2`) or by hand in Play > Advanced settings (listen: players = host + clients). `ue_play` persists these into the editor's PIE settings; restore them afterwards (ConfigSettingsToolset, section `LevelEditor/PlayIn`: `PlayNetMode`, `PlayNumberOfClients`, `RunUnderOneProcess`, `bLaunchSeparateServer`). Do not `time.sleep` inside an editor Python call: it blocks the game thread and the scenario timeline with it. Start the scenario, let the call return, wait ~15 s, then call `report()`: a report taken while the scenario runs shows transient position/stamina differences.
- Input injection is the same path for every player: `hold` / `release` / `press(index, action)` go through the Enhanced Input subsystem of the world's local player. In listen `index 0` drives the host's own pawn; on a dedicated server it raises (no local player). `force_reconcile*` refuse index 0 (the authority never reconciles). Scenarios take a world `index`; targets (`server_apply`, `server_correction`, `accounting`, `server_dash`) default to the pawn key of that world's player (`key_of_player`), since player ids depend on join order.
- What each `CMP` line compares (the authoritative copy is always the one in world 0; position, mode, attributes, tags, combat history as before):
  - `host-local(w0) vs simulated(wN)`: the host's own pawn against a client's view of it (listen only).
  - `server-copy(w0) vs autonomous(wN)`: a client's own pawn against its authoritative copy on the host/server.
  - `server-copy(w0) vs simulated(wM)`: a client's pawn as another client sees it.
  - `CMP RESULT: k/n OK` closes the report; `report(pos_tol, proxy_pos_tol)` can loosen the position tolerance for simulated (interpolated) copies. The first line of `report()` carries the `check_topology()` problems, if any.

- `force_reconcile_on_mode`: forces a reconcile while the client pawn is in a given mode (e.g. on the wall with `GA_WallSlide` active). `np.ForceReconcile` is one global cvar under "Run Under One Process", so it is set again every frame until the target client's rollback counter increases.
- With network emulation on, packet loss (`m.net(60, 15, 2)`) alone causes a few Sync/Aux mismatch reconciles around dashes (seen live in listen: 3 in one `scenario_abilities` run, none at `m.net(60, 15, 0)`), so `unexplained` can be non-zero at 2% loss; judge the code at 0% loss. A clean run = host/server and client snapshots equal after the scenario and **no reconciles that were not forced**, with one known exception (below). Unexpected reconciles almost always mean simulation reads state that is not rolled back (see the rules in gas-npp.md).
- **Known exception (frame-offset resyncs).** Network Prediction re-maps the client's frames to the server's (log: `ReconcileFromInputOffset Old Offset X, New Offset Y`) whenever the server simulated ticks without that client's input, and the client's simulation time jumps with it. Expected causes: turning network emulation on (the added round trip), packet loss, and a hitch. In PIE "Run Under One Process" a hitch stalls server and clients together and costs one offset change per client. With nothing of that kind going on, the offset stays put: 0 changes in 60 s idle at lag 0. Keep the editor's Project Settings tab closed during tests: its image pickers stall the whole process for ~300 ms after editor Python calls. An offset change can make an idle pawn mismatch on the period timer of a periodic effect (`GSTN_GE_StaminaRegen`: "Current period Time MS"), a moving one on Mover. So judge by `mark_log()` before the scenario and `report_reconciles(mark)` after it: `unexplained` (state-mismatch reconciles **not** on the frame of an offset change) must be 0, `forced` counts the `np.ForceReconcile` ones, `max_burst` is the most mismatches in one wall-clock second. The log read is the log of **the editor process the script runs in**, not "the" project log: with two editors open (Development and DebugGame) the second one writes `<Game>_2.log`. `_log_path()` takes `-ABSLOG`/`-LOG` from the command line if present, else writes a unique token (pid + uuid) with `unreal.log`, flushes and picks the `<Game>*.log` that contains it (cached; costs up to ~1 s once). `mark_log` / `report_reconciles` flush first (`unreal.log_flush` if exposed) and wait until the file size is stable (max ~0.5 s) so buffered lines are not missed; a half-written last line is dropped. How the fork recovers from a hitch: `UNetworkPredictionPlayerControllerComponent::AdvanceLastConsumedFrame` and `UNetworkPredictionWorldManager::SendFixedTickInputsToServer`. A client input lost in transit can only be recovered by a redundant copy sent before the server consumes that frame (the gap is filled with the previous input, logged as `Gap in input stream`). Accepting late frames does not help: UE drops reordered packets, and time dilation keeps the server's buffer shallower than the one-way latency, so a late copy always arrives after the frame was consumed (tried and measured, 0 repairs in 30 hitches).

## When to run what

- Changed an ability, tag, effect or anything in the ability tick: run `scenario_abilities` and `scenario_forced_rollback` with lag/jitter/loss on.
- Changed a wall mode or transition, or Mover sync/aux state: run `scenario_jump_wall` (ground jump, grab the wall, wall slide), `scenario_server_correction` on the wall, and `force_reconcile_on_mode` while in the wall mode.
- Changed the combat model (`Plugins/GSTNCombatNP`): run `scenario_combat_spike` (the `Dash` button -> test dash, `HitstopTestButton` -> hitstop window, forced reconciles across both) with lag/jitter/loss; `combat_tap(client, mask)` sends a one-frame press. Turn on `np.PrintReconciles 1` in every world: the harness rollback counter counts each rollback twice, the log shows which ones were forced.
- Command locks (`scenario_combat_lock`, PASS 12 checks on the listen server with the test content below): a stance that owns `Input.Lock.Command.Attack` while its button is held; the dash still activates, an attack press does nothing, releasing the stance while attack is held lets the attack out, a forced reconcile while the stance is held. Uses `combat_hold(client, mask)` / `combat_clear(client)` (scripted held buttons). In listen mode also check that the host's own pawn publishes `Input.Event.CommandExecuted` once per activation (the outbox is drained on the authority, never "when there is no local player").
- Changed input resolution (`GSTNInput` slots, bindings, contexts): `scenario_combat_activation`, `scenario_combat_main_inputs` (run it with `camera_yaw=0` and `90`), `scenario_combat_context`.
- Startup: `abilities_startup(runs=3)` restarts PIE and runs `scenario_abilities` `settle_seconds` (3 s) after every pawn has its input ready, to look for a burst of Sync/Aux mismatches at startup (26 at once were seen on client 2). Poll `abilities_startup_result()`. **Known fork startup burst** (fix proposed: the fork now skips server states ahead of the local pending frame, see PATCHES.md §1; re-run `abilities_startup` to confirm the burst is gone, then remove this note): on every PIE start (6-12 mismatches, bursts up to 12-15, in all runs) the log shows reconciles at `Offset: 0` while a late-joining client's local Mover mode is still `None`, followed by `RollbackFrame N AHEAD of PendingFrame 0` (the rollback is a no-op) and the first `ReconcileFromInputOffset`, all before the scenario starts. It happens before the simulation of that pawn exists, so it is reported (`startup_*` keys) but not judged; the verdict looks only at the scenario window (unexplained mismatches, burst, CMP). It was not compared against a build without the M2 code. The first scenario started right after PIE start without the settle period (`combat_spike` run 1) shows it too: 6 unexplained, and 0 on the rerun. Open item: in the scenario window of a freshly started PIE (3 s after ready, lag 60/15) 2 single mismatches per run remain: the client predicts `Falling` for a pawn standing still on the ground (position and velocity equal), the server `Walking`; CMP is 6/6 at the end, and the same scenario in an already running session shows none apart from the jitter-driven offset changes. Not traced (only Mover state differs in the dump), not seen with the combat scenarios.

### Strict combat scenarios (`_Run`)

`scenario_combat_spike`, `scenario_combat_lock`, `scenario_combat_activation`, `scenario_combat_main_inputs` and `scenario_combat_context` do not just inject input: a sampler records every editor tick, for the authoritative copy (world 0) and the client's own copy, the `Test.*` tags, stamina, cooldowns, Mover mode and the combat request (binding index + 1 and frame), and checks run as timeline steps over windows of those samples. A scenario cannot pass vacuously: every absence ("attack locked: no `Test.State.Attacking`") is paired with a positive precondition (stance active the whole window), the activations assert tag + cooldown + stamina drop, the airborne scenario asserts the pawn is not `Walking`. The verdict is one `unreal.log` line (`log_error` on FAIL) listing every check; `last_checks()` returns `(verdict, [(ok, label, detail)])`. `combat_spike` and `combat_lock` also assert that the forced reconciles happened (total client rollbacks went up; `np.ForceReconcile` is one global cvar, so another client may take it) and that `report_reconciles` has 0 unexplained mismatches. Read `np.PrintReconciles 1` and `report()` as before.

Button names are never indices: `button_index('Attack')` / `button_mask(name)` look up `Input.Button.<Name>` in `/Game/GASNPPTest/Input/IC_GASNPP_Test` at scenario start (an int is still accepted as a raw index), so reordering the buttons in the asset does not break anything. `_require_test_config` refuses to run if the pawn's combat component uses another input config.

### M3 spike probes (`spike_grants`, `spike_stats`, `spike_triggers`)

Live checks of the three M3 spikes (static analysis and numbers: `docs/notes/m3-spike-report.md`). Probe content lives in `GSTN_TestProbeAbilities.h` (trigger abilities, 40 distinct bulk-grant ability classes), `GSTN_TestEffects.h` (`Test.Probe.*` tags and effects) and `UGSTN_TestAttributeSet` (`ProbeEventCount`, `ProbeTagCount`, `ProbeSpeedScale`, `ProbeGravityScale`); nothing is in the test Blueprint's `DefaultAbilities`, the scenarios grant and revoke what they need on the server. `UGSTN_GASNPPTestComponent` has the server-side helpers (callable from Python: `server_grant_bulk(first, count)`, `server_revoke_bulk()`, `server_set_bulk_effect(bool)`, `server_set_stats_preset(0|1|2)`, `server_grant_probe(name)`, `server_revoke_probes()`, `count_owned_bulk_specs()`, `set_stats_probe_enabled(bool)`, `reset_probe_counters()`) and the snapshot gains a `probe` object (owned bulk specs, spec total, active abilities, per-trigger counters, MaxSpeed / gravity in effect) plus the four probe attributes in `attributes`, so `report()` compares them too.

```python
m.setup_editor(True); m.net(60, 15, 0)   # PIE started as above; judge these at 0 % loss (loss causes reconciles of its own)
m.scenario_spike_grants(client=1)        # ~19 s. 40 specs + an infinite effect granted outside the simulation, revoked, a different 20 granted
m.scenario_spike_stats(1, 2)             # ~13 s. two pawns with different speed and gravity scales, forced reconciles across the change and the jump apexes
m.scenario_spike_triggers(client=1)      # ~25 s. GameplayEvent and OwnedTagAdded triggers, forced rollbacks across the activation, swapped grant order
print(m.last_checks())                   # (verdict, [(ok, label, detail)]) once the log shows the verdict; never start another scenario before it
```

Run each with `client=0` too in listen mode (the host's own pawn: no reconcile expected, the owner is the authority). `scenario_spike_triggers(client, fork_patched=False)` turns the "nothing happens while a frame is restored" checks into notes, to measure the unpatched fork (`Plugins/GASNPP/PATCHES.md`, section 1). Not measurable from Python and left as notes: bytes per send of the 40 specs (read `stat net` in the owner's world before and after the grant) and the one-frame cost of creating the 40 instances (Insights). The stats probe rewrites Mover's settings from the component's pre-simulation tick, not from a Mover movement modifier, so queueing a persistent modifier from outside the simulation (L5) is not covered. The raiser abilities activate on the release of `IA_GASNPP_Buff` (the test buff uses its press), and the ability system activates only the first ability found for an (action, event) pair, so grant at most one raiser at a time.
